# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`swift-pwa` is a Swift-native thin-client PWA wrapper around system webviews — a Tauri/Wails analogue for the Swift world. One Swift package, one JS API (`__SWIFT_PWA__.invoke()` / `subscribe()`), one CLI (`swift-pwa`) that produces `.app`, `.ipa`, `.AppImage`, and Windows portable / MSIX from the same source. Status: last tagged release is v0.10.3 (all five platforms first-class). **v0.10.3** is an adopter-feedback release whose three items all turned on measuring rather than believing. (1) **The same record now crosses the bridge as the same bytes**: `JSONEncoder` does not preserve declaration order for synthesized `CodingKeys` — hash order, varying *per encode* (measured: **6 distinct key orders across 200 encodes** with one reused encoder) and again per process — so `JSON.stringify(a) === JSON.stringify(b)`, the obvious way for a page to ask "did this change?", never matched; the reporting adopter's virtualized gallery rebuilt every card on every re-list, which read as the grid flashing once a second. The fix is `.sortedKeys` in **`Envelope.encode`**, *not* on the handler's encoder as suggested — the envelope parses each payload back to `Any` and re-serializes it, so an upstream sort was **undone on the way out**; at the envelope it is also the one choke point all five backends deliver through, so replies, stream/session chunks and `events.*` pushes are covered, nested objects included. Verified against a control build of the released CLI on all four engines (WKWebView: 3 distinct serializations → 1). (2) **HEIC/HEIF/AVIF are served as themselves** rather than `application/octet-stream` — a correctness fix whose *reported symptom did not reproduce*: Apple's WebKit sniffs and rendered them under the wrong type anyway, while WebKitGTK renders them under no type at all. `swift-pwa dev` also had a **second copy** of the MIME table that had already drifted (no audio/video types), now deleted. (3) The finding those two produced is the release's real content: **HEIC renders in exactly one of the four engines** this project ships on (Apple's; Chromium has AVIF but no HEIC, WebKitGTK links neither decoder), while the *platform underneath* the webview decodes it on three of four — so **`image.*`** exposes a decoder every build already contained (`ImageCodec` was `package`-internal, reachable only by the AI backends). Opt-in `ImagePlugin(PlatformImageTranscoder())` behind the new `SwiftPWAImage` product (the `SwiftPWAArchive` shape), serving `image.info` + `image.transcode` on **all five platforms**: ImageIO, `BitmapFactory`, **WIC** on Windows (new `CWicShim`, plain Win32/COM — no NuGet, unlike `CWebView2Shim`), and **libheif on Linux via `dlopen`** (new `CHeifShim`). That last one was expected to cost a `libheif-dev` dependency, AppImage bundling, CI provisioning and an opt-in build flag; `dlopen` removed **all** of it, and the proposal section that predicted otherwise is corrected in place. **`image.info` is load-bearing, not decoration** — what a build can read is genuinely uneven, so it is *derived*: Apple enumerates ImageIO's real type list, Android asks the device (`minSdk` can be 28 while AVIF needs 31), Windows enumerates registered WIC decoders (HEIC needs the paid/OEM HEVC extension — offerable, never promisable), Linux probes `heif_have_decoder_for_format` (libheif dlopens its *own* codec plugins). `E_IMAGE_UNSUPPORTED` is kept distinct from `E_IMAGE` because it answers a question `image.info` could have. The load-bearing test is that **a build claiming a format must actually decode it**, against committed 1.4 KB HEIC/AVIF fixtures, with a clean-refusal assertion where it doesn't. Verified by driving real apps, one measurement per engine that refuses HEIC: the file reports `naturalWidth: 0` and the JPEG from `image.transcode` renders (Fold7 2,934 bytes → 240; Windows x64 3,444 → 240; the same image as PNG is 42,000 / 35,794 bytes, which is how we know `format` reaches the encoder). Reference: [`docs/javascript-api.md`](docs/javascript-api.md#image--convert-an-image-the-webview-cant-display); proposal [`docs/proposals/image-transcode.md`](docs/proposals/image-transcode.md). Two things deliberately left: `ctx.serveDirectory` mounts are unreachable on WebView2 (#159) and `DevServerTests` flakes on a probed-then-rebound port (#161). **v0.10.2** is a performance + observability point release, all of it from one adopter's measurements. **On-device TTS is ~1.5x faster on Apple and desktop**: `QwenTTSBackend` pinned *every* platform to `ORT_ENABLE_BASIC`, a ceiling inherited from a real **Android** constraint (the extended fusions emit `com.microsoft.*` contrib ops, for which the Android ONNX Runtime has no **float16** kernels, and the talker is fp16) that was applied globally and never revisited — Apple/desktop packages *do* carry those kernels, and the transformer fusions are exactly what this pipeline is made of. Level is now platform-derived (`.basic` on Android, `.all` elsewhere); measured RTF **3.70 → 2.52** on an M-series Mac, matching the adopter's independently-reported 3.3x-slower-than-real-time for the old path, with the **audio unchanged** (140,160 samples, correlation 0.999999999822609 — checked because the sampler is *seeded*, so an approximate fusion could have forked the token stream into different-but-plausible speech). **CoreML is plumbed and off, because it loses**: the vendored Apple ONNX Runtime always contained the EP and nothing ever appended it, so every Apple ONNX session silently ran CPU; now requestable via `OrtCoreMLOptions`, but measured it takes 2119 of the talker's 2629 nodes across **170 partitions** against ~750 session runs per utterance, three MLProgram configs are refused at `CreateSession` (`-14`), `NeuralNetwork` loads then dies on the **first token** (a zero-element KV cache — step 0 of every autoregressive generation), and the one config that runs is slower than CPU *and* changes the output. The rule: CoreML pays for one big static-shape graph run a few times, loses for a small dynamic graph run hundreds of times — so `MobileSAMBackend` (a vision encoder, the first shape) is deliberately untouched pending measurement. The adopter's MLX reference (2.5x *faster* than real time on GPU) says the ~8x headroom is real; the road there is a native CoreML/MLX export with bounded KV-cache shapes, not an EP. Two traps: the vendored `coreml_provider_factory.h` documents `MLComputeUnits` spellings the implementation **rejects** (ORT 1.27 takes bare `CPUAndGPU`/`CPUAndNeuralEngine`/`CPUOnly`; "all" = omit the key), and a rejected value throws at session creation which the fallback turns into a *silent CPU run* — the first benchmark showed CoreML matching CPU exactly because it **was** CPU. Hence **`ai.info` now reports `provider`** (`cpu`/`coreml`/`cuda`/`directml`), mirroring `ai.vision.info`, across `QwenTTSBackend`/`StableDiffusionBackend`/`LaMaBackend`/`MultiModelImageBackend` (the router reports whichever model is *resident*); absent rather than `"cpu"` when unknown, cleared by `unload()`. And **`ai.info` no longer queues behind a running generation**: every ONNX backend is an `actor` and `AIPlugin` serves `ai.info` as `await backend.info()`, so a capability read couldn't enter the actor mid-synthesis — reproduced at **6 ms idle vs 9,873 ms** four seconds in, which reached the adopter as a voice picker blank for ten seconds while a book played. `info()`/`modelInfo()` are now `nonisolated` on all three backends with the provider record behind an `NSLock` (0 ms after, also 0 ms during an SD denoise loop); *mutating* entry points stay isolated deliberately, since `unload()` racing a generation would free the sessions under it. Also lands the never-merged **`Scripts/remote-linux.sh`** — which `verify-linux-{ble,permissions}.sh` and a shipped 0.9.x release note already referenced while it existed only on an unpushed branch — plus its `docs/linux-setup.md` fixes (libxml2 2.14 `-rpath-link`; missing `libsecret-1-dev`), and `docs/proposals/serial-plugin.md` as a 0.11 candidate. Benchmarks live in the normal suite (`QwenTTSBenchmarkTests`, opt-in via `QWEN_TTS_BENCH=1`) and interleave configurations, because a straight-through run measured everything ~1.5x slow once the laptop heated up. Reference: [`docs/on-device-ai-performance.md`](docs/on-device-ai-performance.md). **v0.10.1** adds **`ble.*`** — Bluetooth LE on all five, and the one capability here with **no web fallback at all**: Web Bluetooth has never shipped in WKWebView or Safari, and Android's embedded `WebView` doesn't expose it either (Chrome does). So unlike the rest of the device surface this isn't the web API answered properly, it's the difference between the capability existing and not — which is why `bluetooth` is declared under a new **`permissions.device`** key rather than `permissions.web` (no page can ask for it), and why `WebPermission` is now **`DevicePermission`** (old name kept as a deprecated typealias). No new bridge primitives: a connection *is* a duplex session, so `ble.connect` opens with the peripheral, takes writes as pushes and yields notifications downstream, with an optional `token` echoed on the `ack`/`read`/`failed` that answers each push — without it `withResponse: true`, whose whole point is confirmation, has nowhere to report success. A failed operation is a downstream `failed` event, not a stream error (the bridge ends a session on an error, and a rejected write shouldn't cost the page its link), and **a link survives a drop** — `state{connected:false}`, keep trying, re-emit `ready` with fresh handles — because the shape this exists for is a machine that browns out mid-job. **One UUID spelling, both directions:** CoreBluetooth returns `"FFE1"` for an assigned 16-bit UUID and upper-case 128-bit otherwise, BlueZ and Android lower-case 128-bit, WinRT a `GUID` — a page written against one silently matches *nothing* on the others, with no error at all, so the wire is canonicalized to 128-bit lower-case. Backends: CoreBluetooth, **BlueZ over GDBus** (one gio-only shim for both GTK backends — its GATT interface *is* D-Bus), WinRT `Windows.Devices.Bluetooth`, and `BluetoothLeScanner`+`BluetoothGatt` on Android; availability is checked in Core because an adapter that's switched off scans happily and finds nothing, which a page can't tell from an empty room. Verified end-to-end on all five against `Scripts/ble-test-peripheral.*` (three fixtures — macOS, BlueZ, and a portable **LE-only** Android one). **Findings only hardware could produce:** Android's catch-all status 133 had *two* causes — `connectGatt` off the main thread, and `getRemoteDevice(address)` assuming a public address type, so a peripheral advertising a random one is unreachable; Android also serialises GATT strictly (a second op before the first completes returns false silently), and `setCharacteristicNotification` never reaches the peripheral — the CCCD write does. Windows has **no `Connect()`** (reading the service tree *is* the connection) and closes an idle link unless a `GattSession` holds `MaintainConnection`, which surfaces as `ready` firing over and over; a C++ exception unwinding across the shim's C ABI into Swift killed the process with no message. BlueZ raises a `Value` property change for `ReadValue` too, so a read came back to the page as unsolicited data. **The documented limit:** connecting from Linux to a *dual-mode* peripheral (a Mac, a phone) fails `br-connection-key-missing` — it advertises over LE from the same address its classic radio uses, so BlueZ merges the identities and takes the classic route; measured, not assumed (rebuilding the device from an LE-only scan doesn't change its mind, and `bluetoothctl` "succeeds" only by starting a classic pairing), and pairing once is the fix. Guide: [`docs/tutorials/talking-to-a-bluetooth-peripheral.md`](docs/tutorials/talking-to-a-bluetooth-peripheral.md); reference [`docs/bluetooth.md`](docs/bluetooth.md). Two fixes ride along: **one pending `invoke` froze the whole bridge** for that window (pre-existing; `geo.*` is just the first command that can pend indefinitely on user input — invokes now dispatch concurrently while `subscribe`/`unsubscribe`/`push` stay ordered), and the **permission cross-check skipped the case it exists to catch** — it was gated on `pwa.json` having a `permissions` block, so an app declaring in Swift and nowhere else was never compared, which is exactly the scaffold's shape and ends in a refused request on Android or a terminated app on Apple. **v0.10.0** is the **device surface**: before it, **no backend installed a permission handler** — not one of the five — so a page's own `getUserMedia` / `navigator.geolocation` were denied *silently* on three of them, with `PERMISSION_DENIED`, a code meaning *the user said no* about a question nobody asked. Measured on real hardware: `NotAllowedError` in **18–83 ms** and `code 1` in **1–2 ms**, against the 6–7 **seconds** a platform takes when it really asks a human — and on Linux `xwininfo` is byte-identical across the request, so no dialog is ever created. Now `ctx.permissions` is one policy every backend consults: nothing is permitted until declared (so no app silently gains a capability on upgrade, and the formerly-silent refusal names the exact call to add), plus **`setVeto`**, the app's own privacy switch, which sits *above* the OS prompt so a vetoed permission is refused without asking the user about something the app already ruled out. `pwa.json`'s **`permissions.web`** drives the platform artifact (Android `uses-permission`, Apple usage descriptions) and exists separately because a cross-compiled build can't run the app to ask what it declared — the same limit `agent.expose` has; `swift-pwa build` **fails on drift in either direction** and rejects an unknown name before anything is built. It also ships **`geo.*`** (`geo.current` / `geo.watch`) on all five, because macOS WKWebView offers an embedder **no way to grant `navigator.geolocation`** — measured directly: in one process, with location authorized by the user, `geo.current` returns a fix while the web API still reports `code 1 "User denied Geolocation"`. Backends: CoreLocation, **GeoClue 2** over D-Bus (one gio-only shim serving both GTK backends), WinRT `Geolocator`, and Android `LocationManager` (*not* Fused — that would add a Play Services dependency to every generated project for a framework API). Every cell verified on real hardware: fixes of 35 m (macOS), 6 m (iOS), ~26 km (Linux, IP-class), 100 m (Android), 115 m (Windows). **The one documented limit:** on macOS/iOS the app-level veto can't gate the page's own capture — a `WKUIDelegate` handler, installed with `responds(to:)` true for WebKit's exact selector, is **never called** for `pwa://` content; the prompt users see is macOS's own TCC dialog. `geo.*` escapes this because `GeoPlugin` gates in **Core** rather than at a backend seam, which is the transferable lesson. Findings only hardware could produce: an Android microphone needs **`MODIFY_AUDIO_SETTINGS`** as well as `RECORD_AUDIO` or `getUserMedia` fails `NotReadableError` *with the permission granted* (reads as broken hardware); Windows **persisted** the veto's refusal into the WebView2 profile and then stopped raising the event at all, so a switch toggled back on left capture blocked forever (`SavesInProfile(FALSE)`); **CoreLocation denies itself** if asked for a fix while authorization is `.notDetermined`, *and* leaves the app switched off in Settings; Linux needs a running **GeoClue agent** (a desktop session has one, SSH doesn't); and Android discards stdout/stderr, so the diagnostic explaining a silent refusal was itself silent (Core diagnostics now route through an installable sink). Guide: [`docs/tutorials/using-the-camera-and-location.md`](docs/tutorials/using-the-camera-and-location.md); reference [`docs/permissions.md`](docs/permissions.md). **v0.9.12** is three wedges, all found by running things rather than reading them. (1) `Shell.capture` read a child's stdout **after** `waitUntilExit()`, so any command that says more than a pipe holds deadlocks permanently — measured: 64 KiB returns, 128 KiB never does. The command over the line is `xcrun simctl list runtimes -j`, **133,117 bytes on a CI runner** against 21 KB on a Mac with one runtime installed, which is why it only ever failed there; three CI jobs died at their step timeout (39, 30, 45 min) looking like slow compiles, because the hanging call is a *diagnostic* pre-flight that runs before the build prints anything. The tell was in every log from the start: the one orphan process the runner killed was `simctl`, never `xcodebuild` — the v0.9.10 note blamed xcodebuild off the *last line printed* and is corrected. `simulator-drive` now passes in ~5 min, having never once finished. (2) `build --target linux` **aborted** for any app declaring `agent.expose` *and* installing a tray — the combination the agent surface documents, since the indicator is a tray item: validating `agent.expose` runs the app's `configure` headlessly to dump its catalog, before `gtk_init`, and GTK *aborts the process* when asked for a menu with no display. A tray is now inert with no display or during a dump (which also stops the GTK4 D-Bus tray putting a real status item in the user's panel as a side effect of a *build*). (3) `build --target linux` **never returned at all**: `linuxdeploy` is itself a FUSE-self-mounting AppImage, and on that path the `.AppImage` is complete on disk while the CLI waits forever on an exited child whose mount daemon lingers — 84 minutes on a clean box with the *shipped* v0.9.11 binary, on both GTK boxes. `APPIMAGE_EXTRACT_AND_RUN=1` makes the same build take **26 seconds**; nothing on our side of the spawn helps (`waitUntilExit`, polling `isRunning`, `terminationHandler` all wait alike). The sting: the release workflow `swift-pwa init` generates had set that very variable since it was written, so the workaround lived in the generated copy and never in the tool. The CI gap behind (2) and (3) is closed by **`bundle-smoke-linux`** — nothing here had ever bundled an AppImage; it scaffolds a fresh app, bundles, deletes `.build`, relocates, launches under Xvfb and drives it. Also queued as a 0.10 candidate: `docs/proposals/ble-plugin.md`. **v0.9.11** fixes the macOS app driver's keyboard, found by an adopter driving a real reader app: every *named* key (arrows, `Enter`, `Tab`, `Escape`, `Backspace`) arrived in the page as **`key: "Dead"`** because it was synthesized with `characters: ""`, and an empty string isn't "no character" to WebKit — it's a dead key. `code` and `keyCode` were correct throughout, which is what made it so misleading. Named keys now carry what macOS sends (AppKit's private-use code points + `function`/`numericPad` flags; control characters for the editing keys), `Backspace`/`Delete` are no longer the same virtual key code, and `Home`/`End`/`Page*`/`Insert`/`F1`–`F12` exist at all. Every unhandled synthetic keystroke also **beeped** audibly on the host — AppKit's `noResponder` feedback, which a scope around `sendEvent` can't suppress because WebKit re-sends unhandled events asynchronously, so injected events are recognised by timestamp instead. And because WebKit **throttles `requestAnimationFrame` for a window the compositor isn't showing** (measured: 1 frame in 3s minimized vs 183 visible), a page that draws in a rAF callback silently does nothing while covered while `drive shot` returns a clean screenshot of the stale state — so `Window.visibility()` now reports occlusion (macOS properly, Windows minimized-only, Linux/Android `unknown`) and every verb warns. **v0.9.10** is an adopter-feedback release whose headline is that a bundled app was never self-contained: `bridge.js` came from a SwiftPM resource bundle, and the generated `Bundle.module` accessor resolves either to the bundle *root* (where codesign refuses to seal) or to an absolute path inside the **build machine's** `.build/` — so every `.app`, AppImage and portable `.exe` worked where it was built and hard-crashed on launch anywhere else. The text is compiled into the binary now (`BridgeJSData`), Core declares no resources at all, and CI's `bundle-smoke` job scaffolds → bundles → deletes `.build` → relocates → drives. Alongside it: **per-target output directories** (`build/macos`, `build/ios`, `build/ios-simulator`, …) plus a refuse-to-clobber guard, so an iOS deploy can't overwrite a macOS `.app` and leave a bundle that fails to launch for reasons pointing at signing; repeatable **`--arch`** for a universal macOS binary; **`--configuration debug|release`**; **`swift-pwa drive --simulator`** (the iOS Simulator shares the host's loopback, so the driver just works there — no synthetic input, and a device can't be driven at all); an AppImage that stages `web/` beside the binary instead of an unresolvable `usr/share/<exe>/web`; and bounded `simctl` calls, because one wedged for 39 minutes in CI with no output. ## Architecture

The package is layered as **core → backend → umbrella**:

- **`SwiftPWACore`** (platform-agnostic) — defines `AppRuntime`, `AppContext`, `Window`, `PWAWebView` protocols; the `BridgeRuntime`, `CommandRegistry`, `Invocation` envelope, `Plugin` model, and the built-in `WindowPlugin` exposing `window.*` JS commands. Also ships `Resources/bridge.js`, the JS-side runtime injected at document-start.
- **`SwiftPWAWebKit`** ([Sources/SwiftPWAWebKit/](Sources/SwiftPWAWebKit/)) — Apple backend (macOS 15+, iOS 18+) wrapping `WKWebView` with a `pwa://` scheme handler and UIScene multi-window scaffolding. Conditionally compiled `.when(platforms: [.macOS, .iOS])`.
- **`SwiftPWAGTK`** — Linux backend, hand-rolled C shims. Two parallel implementations selected at build time via the `SWIFT_PWA_GTK4` environment variable read in [Package.swift](Package.swift):
  - **Default** (GTK3 + WebKitGTK 4.1): sources in [Sources/SwiftPWAGTK/](Sources/SwiftPWAGTK/) + [Sources/CGtk3Shim/](Sources/CGtk3Shim/) + [Sources/CWebKitGTK4Shim/](Sources/CWebKitGTK4Shim/).
  - **`SWIFT_PWA_GTK4=1`** (GTK4 + WebKitGTK 6.0): sources in [Sources/SwiftPWAGTK4/](Sources/SwiftPWAGTK4/) + [Sources/CGtk4Shim/](Sources/CGtk4Shim/) + [Sources/CWebKitGTK6Shim/](Sources/CWebKitGTK6Shim/).
  - Both export the same `SwiftPWAGTK` Swift module name (Package.swift swaps `path`), so the umbrella and downstream code don't change. Conditionally compiled `.when(platforms: [.linux])`.
- **`SwiftPWA`** (umbrella) — the only module users import. `@_exported`s core + the platform backend, exposes `SwiftPWA.runtime()` which returns the platform-appropriate `AppRuntime`.
- **`swift-pwa-cli`** — `init`, `dev`, `build` subcommands; bundlers for `.app` (Mac), `.ipa` (iOS via `xcodebuild`), `.AppImage` (Linux via `linuxdeploy`); `pwa.json` is the source of truth for `Info.plist`/`.desktop`/icon generation.
- **`_SwiftPWATestSupport`** — reusable `MockWindow` / `MockWebView` / `MockAppContext` consumed by all test targets.

### The bridge

JS↔Swift uses a Tauri-style envelope `{v, kind, id, cmd, payload}`. Every backend webview adapter funnels inbound `invoke` / `subscribe` / `unsubscribe` frames through `BridgeRuntime.handle`, which dispatches into a single `CommandRegistry`. Outbound frames go through `webView.deliver(...)` (`reply` / `replyError` / `event` / `end`). `invoke` is unary; `subscribe` is streaming (each yield from a typed handler becomes an `event` frame, completion becomes `end`).

### Concurrency model — important

This is the trickiest part of the codebase and the source of past bugs:

- **`CommandRegistry` is a class, not an actor.** It uses `NSLock` and `@unchecked Sendable`. Registration is *synchronous* on purpose so user `configure` closures can run on a thread that isn't pumping Swift's MainActor executor (e.g. before `gtk_main()` enters its loop on Linux).
- **`BridgeRuntime` is *not* `@MainActor`.** Its pump task runs on the cooperative pool. Backend `PWAWebView.deliver` implementations are responsible for hopping to the platform UI thread internally. The previous `@MainActor`-ised design hung on Linux because `gtk_main()` doesn't drain libdispatch's main queue, which is what Swift's MainActor is backed by.
- **`MainThread.run` ([Sources/SwiftPWACore/MainThread.swift](Sources/SwiftPWACore/MainThread.swift)) is the canonical "run this on the UI thread" abstraction.** It routes through a per-backend dispatch hook installed at startup: Apple registers a `DispatchQueue.main`-based hook, GTK registers one that schedules via `g_idle_add`. The closure stays `@MainActor`-annotated; `MainActor.assumeIsolated` satisfies the runtime check once execution lands on the UI thread. Use this rather than `await MainActor.run` in any code path that may execute under `gtk_main`.

### Linux backend caveats

- **Two parallel backends, picked at build time.** `SWIFT_PWA_GTK4=1` swaps which directory contributes the Swift sources for the `SwiftPWAGTK` target and which C shims it depends on. Both expose the same Swift class names (`GTKWindow`, `GTKAppContext`, `GTKAppRuntime`, `WebKitGTKAdapter`) so the umbrella and tests don't branch. Don't try to import both at once — only one is in the package graph per build.
- **`Window.position()` / `setPosition` / `.didMove` are no-ops on the GTK4 backend.** GTK4 dropped the position API; Wayland refuses to give apps their own position. The cross-platform `Window` protocol documents this as best-effort.
- The GTK3 C shim assumes the **WebKitGTK 4.1 ABI** specifically — `WebKitJavascriptResult` is a boxed type (not a GObject) on the script-message callback. The GTK4 shim handles the 6.0 ABI where the same callback receives a `JSCValue*` directly.
- **`webView.evaluateJavaScript(_:)` bridges the `GAsyncResult` callback chain back into a Swift `CheckedContinuation`** via the `swiftpwa_evaluate_javascript` shim. The result string is the JSON serialization of the JS value (or `nil` for `undefined`). Errors are surfaced as `BridgeError(code: E_HANDLER)`.
- `GtkWidget*` is laundered through `UInt` for strict-concurrency compliance (see commit 3da4f03).

## Conventions

- `swift-tools-version:6.0` enables strict concurrency by default. **Do not** add `enableUpcomingFeature("StrictConcurrency")` — under Swift 6 on Linux it is treated as an error rather than a warning. Only `ExistentialAny` is opted in. See the comment block at the top of [Package.swift](Package.swift).
- swiftformat config: 4-space indent, 120 max width, `--self remove`, `--stripunusedargs closure-only`. Examples are excluded.
- Tests use **swift-testing** (`@Test`, `#expect`), not XCTest.
- **Cross-platform parity is the default.** If a feature lands on one backend (Apple `SwiftPWAWebKit` or Linux `SwiftPWAGTK`), implement the equivalent on the others in the same change — adapted to each platform's HIG / norms rather than ported literally. Example: Mac's Cmd+Q lives in an `NSApplication` menu; the Linux equivalent is a `GtkAccelGroup` Ctrl+Q binding plus quit-on-last-window-closed (Mac keeps the menu bar after last window; Linux exits). If parity isn't feasible in the same change, document it in [docs/linux-setup.md](docs/linux-setup.md)'s "Known limitations" section (or the equivalent platform doc) so users aren't surprised.
- **Docs travel with code changes.** Each behavioral change ships with a doc update in the same commit (or commit pair). The relevant surfaces:
  - User-visible CLI flags / output format → [README.md](README.md) and the matching [docs/&lt;platform&gt;-setup.md](docs/).
  - Per-backend behavior or known limitations → the relevant [docs/&lt;platform&gt;-setup.md](docs/) "Known limitations" section.
  - Anything affecting the public Swift API or `pwa.json` schema → [README.md](README.md)'s API / configuration sections.
  - Always: a `## [Unreleased]` entry in [CHANGELOG.md](CHANGELOG.md) with the *why*, not just the *what*.

  If you change behavior and don't update docs, the next person working in the area finds the docs lying — and the friction of "do I trust the doc or the code?" is what we're trying to avoid. When in doubt, grep the docs for the file / symbol you just changed; anything that mentions it gets a once-over.
- **README is marketing-facing; deep walkthroughs live under [docs/](docs/).** [README.md](README.md) is the elevator pitch — what the project is, the headline feature list, a one-line pointer to where the detail lives. Multi-step tutorials, per-subcommand option tables, worked examples, and feature-specific deep dives belong in a dedicated doc under `docs/` (existing examples: [docs/auto-updates.md](docs/auto-updates.md), [docs/linux-setup.md](docs/linux-setup.md), [docs/windows-setup.md](docs/windows-setup.md)). When you're tempted to add a new `### <feature>` block to README with more than ~5 lines of how-to content, write it in the relevant `docs/` file instead and add a one-line mention + link in README. Rationale: README is the first thing a prospective user reads — too much detail buries the pitch and pushes the "does this solve my problem?" answer below the fold.
- **README writes to the *current state*, never a per-version changelog.** [`CHANGELOG.md`](CHANGELOG.md) is the single home for the release-by-release story; the README must not grow a running "New in v0.8.x / v0.8.y / …" digest anywhere — not at the top (the intro/status is a stable pitch + capability bullets, updated only when a *headline* capability changes, not every point release) and not in the **Roadmap** (which is *forward-looking only* — shipped items get deleted and pointed at CHANGELOG, not left as `(released)` entries). If you catch a per-version list accumulating in README, that's the smell to collapse it into current-state prose. The `## [Unreleased]` CHANGELOG entry is still required for every behavioral change (see the docs-travel-with-code rule above).
- **When a new plugin / capability ships, add it to the README [feature matrix](README.md#feature-matrix)** (with a footnote for per-platform nuance / opt-in flags), and grep the README for stale hedges (`isn't … yet`, `not generated`, `stub`, `Next: …`) that the change now contradicts — the matrix, its footnotes, and the Roadmap must agree with each other and with the code. Keep matrix source rows pipe-aligned to the header (superscripts are multibyte, so count code points, not bytes — the MD060 linter checks pipe columns).
