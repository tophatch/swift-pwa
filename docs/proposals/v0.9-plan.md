# v0.9 plan

Working plan for the 0.9 milestone. We take these **one at a time**, each as its
own PR with docs + a `## [Unreleased]` CHANGELOG entry, device-verified where it
touches a backend or UI.

## Where 0.9 already stands

The last tag is **v0.8.13**. `## [Unreleased]` in [CHANGELOG.md](../../CHANGELOG.md)
already holds the bulk of 0.9 and is release-worthy on its own:

- Bidirectional bridge sessions (duplex streaming)
- Typed JS↔Swift codegen (`swift-pwa codegen`)
- GTK4 system tray (StatusNotifierItem over GDBus)
- Delta / binary-patch updates + background auto-check + mandatory-update kill-switch
- Desktop updater verified end-to-end + hardened; HelloPWA updater test rig
- On-device Stable Diffusion OOM fix (`ai.unload` + low-memory eviction)
- Examples card-deck / light-mode redesign (this PR)

So 0.9 does **not** need new headline work to ship — the items below are about
closing the most-cited gap (on-device audio) and a few cheap wins, then tidying
docs before we tag.

## Item 1 — On-device audio (TTS) generation backend  *(headline)*

**Why.** Text ✅ and image ✅ on-device backends ship on every OS. The
`ai.generateAudio` **contract has been complete since 0.7 with no backend** —
only an implementation guide. Shipping one makes "all three modalities run
on-device" true. Roadmap #2.

**Contract already in place** (no Core changes needed to start):
- [`Sources/SwiftPWACore/Plugin/AI.swift`](../../Sources/SwiftPWACore/Plugin/AI.swift):
  `AIBackend.generateAudio` / `generateAudioStream` (default impl wraps the
  one-shot in a single `done`), `AIGenerateAudioRequest`, `AIGenerateAudioResult`,
  `AIAudioChunk`, `AIAudio`, `AICapabilities.audioGeneration` / `.voiceCloning`.
- `AIModelCapability.textToSpeech` in
  [`AIModelInfo.swift`](../../Sources/SwiftPWACore/Plugin/AIModelInfo.swift).
- `ai.generateAudio` / `ai.generateAudioStream` already routed in
  [`AIPlugin.swift`](../../Sources/SwiftPWACore/Plugin/AIPlugin.swift).
- Guide: [docs/ai-plugin.md](../ai-plugin.md) §"Audio generation (text-to-audio / TTS)".

**Recommended model: Qwen3-TTS-0.6B (Apache-2.0).** Evaluated against the stack
(July 2026 — an on-device export ecosystem now exists):

- **On-device exports exist.** ONNX incl. **INT8** (`sivasub987/Qwen3-TTS-0.6B-ONNX-INT8`,
  ~1.6 GB), CoreML (`FluidInference/qwen3-tts-coreml`), GGUF (`predict-woo/qwen3-tts.cpp`);
  reference ONNX pipeline `elbruno/ElBruno.QwenTTS`. Original weights: PyTorch, 0.6B / 1.7B.
- **Raw text input — no phonemizer.** Takes text via the Qwen BPE tokenizer; this
  **removes the G2P blocker** that made Kokoro/Piper risky. The single biggest
  reason to prefer it.
- **Apache-2.0** — commercial-friendly (matches the LCM-as-commercial-default stance).
- **Voice cloning is built in.** A `speaker_encoder` graph + reference audio maps
  straight onto the **already-shipped** `AICapabilities.voiceCloning` +
  `AIGenerateAudioRequest.referenceAudio`/`referenceText` (0.7.7) — a contract no
  backend exercises yet.
- **Fits the ONNX tier.** `SwiftPWAONNX` `OrtModelSession` already runs INT8/fp16
  multi-graph pipelines (SD / LaMa / MobileSAM); model via `SwiftPWAModelStore`
  (checksum-pinned, resumable).

**Honest complexity flag — this is the most involved on-device pipeline yet.** The
0.6B INT8 export is **9 ONNX graphs**: `text_project` → `talker_prefill` +
`talker_decode` (an **autoregressive loop with host-driven KV cache** — prefill
once, decode per step, like SD's denoise loop but with KV-cache tensors + token
sampling) → `code_predictor` (+ embed) → 12 Hz audio codec (`tokenizer12hz`
encode/decode) → `speaker_encoder` (voice cloning). Two genuinely new pieces
beyond wiring graphs: a **Qwen BPE tokenizer in Swift** (the SD path has
`CLIPTokenizer`; this needs the Qwen vocab equivalent, tokenizer files from
`Qwen3-TTS-12Hz-0.6B-Base`) and the **AR sampling loop + KV-cache management**.

**Stage it to retire that risk (the SD-Turbo-vs-diffusers pattern):**

- **Phase A — desktop spike (decides in/out for 0.9).** Stand up the full 9-graph
  pipeline on one desktop OS (macOS or the Linux box) from Swift over
  `OrtModelSession`, port/verify the Qwen tokenizer, prove the AR loop, and
  **match a reference WAV** from the original pipeline (correlation check, as SD
  did). Retires the tokenizer + AR-loop + codec unknowns before any cross-platform work.
- **Phase B — ship as a backend.** New `SwiftPWAQwenTTS` target (`AIBackend`,
  `audioGeneration: true`, `voiceCloning: true`), `ai.qwen_tts` opt-in
  (matches `ai.local_llama` etc.), model via `ModelStore`; `ai.generateAudio` /
  `ai.generateAudioStream` (stream partial PCM as the codec decodes). Wire
  `referenceAudio` → `speaker_encoder`.
- **Phase C — reach + demo.** Android (ONNX INT8 on the Android ORT AAR — watch
  INT8/fp16 kernel coverage, cf. the SD Gelu-fusion gotcha), a demo arm, and
  (optional) a CoreML fast-path on Apple if ORT latency disappoints.

**Optional lightweight fallback (separate, low-effort, decide after the spike).** A
**platform system-TTS** backend (`AVSpeechSynthesizer` / Android `TextToSpeech` /
WinRT `SpeechSynthesizer`) as a zero-download floor and Linux coverage (where a
1.6 GB AR model is heavy). Not required if Qwen3-TTS lands.

**Verification.** Device: generate a WAV on Android (Fold7) + macOS, confirm
`ai.info().audioGeneration === true` and a playable clip; a CritterFacts demo arm 
that speaks a generated fact. Unit: WAV header / duration sanity, streaming `done` 
semantics.

**Scope boundary for the first PR:** Phase A only (platform system TTS), with a
demo arm. Phase B (neural ONNX) is a separate PR gated on the G2P spike.

**Effort:** Phase A ≈ medium (one conformance per OS + Kotlin/WinRT glue).
Phase B ≈ large (G2P is the unknown).

## Spike findings — Item 1 Phase A (Qwen3-TTS on the ONNX tier)

Ran a desktop spike against `elbruno/Qwen3-TTS-12Hz-0.6B-CustomVoice-ONNX` (a clean
4-graph fp32 ONNX export: `talker_prefill`, `talker_decode`, `code_predictor`,
`vocoder`, with embeddings as `.npy` and the Qwen BPE tokenizer). Verdict: **viable
on the ONNX tier — recommend proceeding to Phase B**, with one real prerequisite
(quantization) called out below.

**Proven (macOS, onnxruntime 1.27 CPU EP):**
- **All four graphs load + initialize on the plain `CPUExecutionProvider`**, and the
  **vocoder produces correct audio**: 30 codec frames → 57,600 samples (2.40 s @
  24 kHz, exact 1920× upsample), in ~500 ms. So the codec — the step that was
  **broken in the INT8 export** (`ConvInteger` ops the CPU EP can't run) — works in
  the fp export on the standard EP the desktop/Android tiers use.
- **Pipeline fully mapped** from the C# `Core` reference (a complete, readable port
  spec): tokenize (Qwen2 BPE, chat template + TTS special tokens) → host-side text
  embed + 2-layer projection (2048→1024) + codec **prefix** (think/lang/speaker/pad/
  bos control tokens; 9 preset voices as codec ids; 12 languages) → `talker_prefill`
  → **nested AR loop** (`talker_decode` samples codebook-0/step; 5-layer
  `code_predictor` fills codebooks 1–15 with its own per-step KV; sum-embed the 16
  codes + streamed trailing-text hidden → next decode step; min 2 tokens; stop on
  `codec_eos` 2150) → assemble `(1,16,T)` → `vocoder` → 24 kHz WAV.
- **Raw text in, no phonemizer** (confirmed — G2P risk is gone). Apache-2.0.

**Risks / real costs for Phase B (quantified):**
1. **Shipping size — the gating item.** fp32 is **~5.9 GB** (talker weights 1.77 GB
   ×2, text-embedding table 1.24 GB). Phones need fp16/quant, **and it must keep the
   codec CPU-runnable** — the one INT8 export on HF breaks exactly that (ConvInteger).
   So Phase B's *first* sub-task is producing/validating a CPU-friendly fp16 (or
   selective-INT8) export, echoing the SD fp16-ORT saga. Until that's solved, this is
   desktop-only.
2. **Port volume.** Nested AR + KV stacking (prefill emits 56 KV tensors that decode
   wants stacked into `(28,·)`) + M-RoPE position_ids + a Qwen BPE tokenizer in Swift
   + sampling (temp/top-k/top-p + repetition penalty). Substantial, but every piece
   is concrete and deterministically testable, and `OrtModelSession` already supports
   the tensor types + host-driven loops (SD's denoise loop is the same shape).
3. **Stochastic decoding** (temp 0.9 / top-k 50 / rep-penalty) — so validate the port
   by forcing **greedy/argmax** for deterministic token-for-token parity vs a golden,
   plus a perceptual pass on sampled output.

**Reference golden — done (on the GPU box).** Generated a PyTorch reference WAV on
`bminisaix1p` (RTX 5080): a fresh CUDA venv (torch 2.11+cu128) + the `qwen-tts`
package + `Qwen/Qwen3-TTS-12Hz-0.6B-CustomVoice`. `generate_custom_voice(text,
speaker="ryan", language="english")` → 7.60 s of 24 kHz mono in 5.2 s on GPU (peak
3.68 GB VRAM), speech-shaped envelope (RMS 0.079, ~23% silent frames). This is the
independent reference to validate the ONNX pipeline against. (Box gotchas: the
existing `sd-work` venv is CPU-only torch with an ABI-broken torchaudio; needed a
fresh cu128 venv. The RTX 5080 is Blackwell sm_120 — cu128+ wheels required.)

**ONNX pipeline + quant A/B — done (on the box), with a key finding.** Built the full
Python ONNX pipeline (tokenizer → prefix → prefill → nested AR → vocoder) from the C#
spec. Prefill is verified correct (confident, sane group-0 prediction on the real
prompt; EOS appropriately low-ranked at frame 0), and the AR loop produces plausible
codec trajectories on the real graphs — so the pipeline is fundamentally sound. Two
things remain for Phase B, not gross bugs: **greedy doesn't emit EOS** for short text
(classic AR-TTS non-termination) and **sampled decoding over-ran/clipped** — both need
per-step validation against the torch reference (which is exactly the Swift-port work).

The **int8-vs-fp32 fidelity A/B, on real in-distribution inputs**, is the important
result:
- **code_predictor int8 ≈ lossless** — logit cos **0.9993**, top-1 match, top-10 10/10.
- **talker int8 measurably perturbed** — g0 logit cos **0.79**, and the **argmax flips**
  (fp32→1995 vs int8→404; top-10 overlap 8/10). Dynamic int8 on the 28-layer talker
  shifts its output distribution enough that **int8 quality ≠ fp32 quality** — it would
  likely degrade audio.
  (NB: an earlier "cos 0.55" number was on *random* inputs — out-of-distribution and
  invalid; the real-input 0.79 is the one that counts.)

**Revised quant recommendation:** don't ship naive int8-dynamic on the talker. Keep
**int8 for code_predictor** (lossless) + **fp16 for the talker** (quality-safe): fp16
talker ≈ 890 MB each → two graphs ~1.78 GB, or **~2.2 GB total** once prefill/decode are
merged into one graph (the redundant-weights optimization), fp16 embeddings + fp32
vocoder. Still less than half of fp32, and quality-preserving. **Open check for Phase B:**
confirm the fp16 talker runs on the CPU EP (fp16 CPU-kernel coverage — cf. the SD
Gelu-fusion gotcha); if not, fall back to per-channel/static int8 with calibration.

**Still open (Phase B proper):**
- Merge prefill/decode; fp16 talker export + CPU-EP check; per-step validation of the
  pipeline against the torch golden (fix termination); then the Swift `SwiftPWAQwenTTS`
  backend over `OrtModelSession`.

**Phase B progress — quantization (the gating risk) retired.** Produced a
CPU-runnable quantized export locally: **int8 dynamic** on the transformer graphs
(`MatMul`→`MatMulInteger`, which the CPU EP supports — unlike the codec's
`ConvInteger`), **fp32 vocoder** left intact (only 459 MB, already CPU-verified),
**fp16** embedding tables. Result: **~2.2 GB total (down from 5.9 GB)**, and all four
graphs load together on the `CPUExecutionProvider`; the quantized `talker_prefill`
executes a forward pass correctly. Per-graph: talker prefill/decode 1779→448 MB each,
code_predictor 441→111 MB, text-embedding table 1245→622 MB. **Further headroom:**
prefill and decode are separate 448 MB files with identical weights — merging them
into one graph (past-KV optional) saves ~448 MB → **~1.7 GB**. Still *unproven*:
that int8 accuracy preserves audio quality — needs the golden-WAV A/B (deferred).

**Recommendation:** **In for 0.9, sequenced.** Phase B order: (1) ✅ CPU-runnable
quant export — **done** (~2.2 GB, all graphs on CPU); next, an int8-vs-fp32 quality
A/B once a golden exists, and the prefill/decode merge;
(2) an independent golden WAV via the reference (approve a local .NET install, or a
torch venv); (3) Swift `SwiftPWAQwenTTS` backend over `OrtModelSession`, validated
greedy-deterministic against the golden. If the quant step proves intractable, fall
back to shipping Qwen3-TTS desktop-only + the platform system-TTS backend on mobile.

### Phase B.1–B.3 — DONE, pipeline verified end-to-end (2026-07-16)

All the research/validation sub-tasks are complete; only the Swift port (B.4) remains.

**B.1 fp16 talker on CPU EP — done + quality-safe.** fp16 talker runs on the CPU EP
(uniform fp16 conversion via `onnxconverter_common`, `del graph.value_info`, retarget the
one baked `.to(float32)` RoPE Cast → fp16, session graph-opt BASIC). Real-input A/B vs fp32:
prefill g0 cos **1.00000**, 8 decode steps 0/8 argmax flips (int8 talker was cos 0.79 / flips
— so fp16, not int8, for the talker).

**B.2 decode-only (drop the prefill graph) — done.** Prefill and decode share identical
weights; feeding the prompt one token at a time through the DECODE graph with growing KV
reproduces the prefill graph EXACTLY (logits + KV cos 1.000000, fp16 & fp32). Ship the
decode graph only (892 MB, halves the talker); prefill = a P-step warm-up loop.

**B.3 termination bug — root-caused + fixed.** Two compounding bugs (found by diffing
against the torch reference): **(1)** the golden uses **non-streaming** mode (full text in
the prefill, `trailing_text_hidden = tts_pad` constant), not the streaming layout my pipeline
had; **(2)** the code_predictor's codebook-1 logits were read from the wrong sequence
position (`[0,0]` — the past-hidden slot — instead of the last position `[0,-1]`; the first
cp call feeds a 2-token input), corrupting codebook 1 every frame → clipping + no EOS.
Every component now verified numerically exact vs torch (prefill/decode teacher-forced cos
1.00000; cp logits cos 1.00000 all 15 codebooks; vocoder on torch's codes bit-for-bit
matches torch native). **Full sampled pipeline matches the reference**: fp32 = 48 frames /
3.84 s / peak 0.568 / clean EOS (torch: 55-70 fr / 4-5.6 s / peak 0.5-0.6).

**Precision config A/B (free-running, sampled):** fp16 talker + fp32 cp = 4.72 s (near-ref);
fp32 + int8 cp = 6.40 s; **fp16 + int8 = 14.56 s** — the two quant steps *compound* under
chaotic sampling (per-step "lossless" cos doesn't imply trajectory parity). All terminate,
none clip. **Recommended shipping config: fp16 talker + fp32 cp + fp32 vocoder** (~2.4 GB,
quality-matched); int8 cp is smaller (~2.1 GB) but drifts longer.

### Phase B.4 — DONE, Swift backend shipped + E2E-verified (2026-07-16)

New opt-in target `SwiftPWAQwenTTS` (product + Package.swift block after the SD one, gated on
`canImport(ONNXRuntime*)` like the other ONNX backends): `QwenTokenizer` (Qwen2 byte-level BPE),
`QwenNumpy` (mmap `.npy`, lazy rows), `QwenTTSConfig`/`QwenTTSModelSpec`, `QwenTTSEmbeddings`
(textProj + codebook lookups), `QwenSampler` (seeded RNG + HF-faithful g0/cp), `QwenWAV`, and
`QwenTTSBackend` (an `AIBackend` actor on `ai.generateAudio`, id `qwen-tts`) — the exact
B.1–B.3 pipeline: non-streaming prefill, decode-only talker warm-up, the talker/code-predictor
AR loop (with the `[0,-1]` cp read + an empty-KV first step), vocoder → 24 kHz WAV, 9 preset
voices. Core: added `AIBackendID.qwenTTS`; `OrtModelSession` now accepts zero-element input
tensors (empty KV cache) — verified non-breaking against the existing int/fp16 tests.

**Verified:** builds against real ONNX headers; 15 unit tests green including the tokenizer
reproducing the reference token ids exactly; swiftformat clean. **E2E on the real 3 GB models**
(macOS, CPU EP): loaded every graph, ran the full Swift pipeline, terminated on the codec EOS,
and produced clean non-clipping speech — with the shipping precision (fp16 talker + fp32
code-predictor + fp32 vocoder + **fp16 text-embedding**, ~2.5 GB, re-verified after the fp16
conversion). Docs updated (CHANGELOG, README matrix audio row + Roadmap, docs/ai-plugin.md).

**B.4 follow-ups (not done):** a hosted model + `ai.ensureModel` download tier (fixed-path
only today); a `CritterFacts` TTS demo arm; on-device (Android) verification; arbitrary-reference
voice cloning (the Base model, mapping to the 0.7.7 `voiceCloning`/`referenceAudio` contract).
